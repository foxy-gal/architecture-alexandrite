# Анализ системы в контексте мониторинга

## Компоненты

- **Online-магазин (B2C)** — оформление заказов через веб-интерфейс
- **API заказов** — используется внешними клиентами и партнёрами
- **MES API** — центральный сервис обработки заказов
- **CRM** — работа с заказами и клиентами
- **PostgreSQL** — хранение данных заказов и клиентов
- **Операторы (MES UI)** — обрабатывают заказы через интерфейс

## Риски и особенности

- Заказы создаются не только через сайт, но и через API. Яндекс Метрика больше не отражает реальный объём заказов
- MES API — единая точка отказа
- Отсутствует прозрачность:
    - где теряются заказы
    - где возникают задержки
    - какая часть проблем связана с API, а какая — с операторами или БД
- Нет технических и бизнес-метрик


# Мотивация внедрения мониторинга

## Что даёт мониторинг бизнесу

1. Снижение потерь выручки
   - Быстрое обнаружение проблем с заказами
   - Сокращение времени простоя и деградаций

2. Повышение удовлетворённости клиентов
   - Контроль SLA по обработке заказов
   - Снижение количества просроченных заказов

3. Прозрачность работы API
   - Понимание реальной нагрузки от внешних клиентов
   - Контроль влияния API-интеграций на основной бизнес

4. Основа для масштабирования
   - Данные для принятия решений о масштабировании сервисов
   - Возможность безопасного роста B2B-направления

5. Снижение стоимости инцидентов
   - Быстрое определение причины сбоя
   - Сокращение MTTR (Mean Time To Recovery)

# Выбор подхода к мониторингу

## MES API, Online-магазин, API заказов 

Подход: RED (Rate, Errors, Duration

Причина:
- Сервисы ориентированы на обработку запросов
- Важны скорость, ошибки и пропускная способность


## PostgreSQL
Подход: USE (Utilization, Saturation, Errors

Причина:
- База данных — ресурс с ограниченной ёмкостью
- Критично понимать загрузку и насыщение

## Бизнес-процессы (заказы)
Подход: Четыре золотых сигнала
- Latency
- Traffic
- Errors
- Saturation

Причина:
- Нужно связать технические проблемы с бизнес-результатами

# Выбор метрик

## RabbitMQ

### Number of dead-letter-exchange letters in RabbitMQ
**Зачем нужна:**  
Показывает количество сообщений, которые не были обработаны и попали в dead-letter-очередь.  
Рост значения указывает на логические ошибки обработки заказов или деградацию downstream-сервисов.

**Ярлыки:**
- `queue`
- `exchange`
- `reason`

### Number of message in flight in RabbitMQ
**Зачем нужна:**  
Позволяет понять текущую нагрузку и наличие «затора» в обработке сообщений.  
Резкий рост — признак того, что потребители не справляются с нагрузкой.

**Ярлыки:**
- `queue`
- `consumer_group`

## Internet Shop API

### Number of requests (RPS) for internet shop API
**Зачем нужна:**  
Показывает общую нагрузку со стороны B2C-клиентов.  
Используется для анализа пиков и планирования масштабирования.

**Ярлыки:**
- `endpoint`
- `method`

### Number of requests (RPS) per user for internet shop API
**Зачем нужна:**  
Позволяет выявлять аномальную активность отдельных пользователей и ботов.

**Ярлыки:**
- `user_id`
- `ip`

### Response time (latency) for shop API
**Зачем нужна:**  
Ключевая метрика пользовательского опыта.  
Рост latency напрямую влияет на конверсию и количество брошенных заказов.

**Ярлыки:**
- `endpoint`
- `method`

### Number of HTTP 200 for shop API
**Зачем нужна:**  
Отражает количество успешно обработанных запросов и используется как базовая бизнес-метрика.

**Ярлыки:**
- `endpoint`

### Number of HTTP 500 for shop API
**Зачем нужна:**  
Показывает количество серверных ошибок, напрямую влияющих на потерю заказов.

**Ярлыки:**
- `endpoint`
- `error_type`

### Number of simultaneous sessions for shop API
**Зачем нужна:**  
Помогает оценить реальное количество активных пользователей и нагрузку на систему.

**Ярлыки:**
- `region`

### CPU % for shop API
**Зачем нужна:**  
Позволяет выявлять перегрузку приложения и необходимость масштабирования.

**Ярлыки:** не требуются

### Memory Utilisation for shop API
**Зачем нужна:**  
Позволяет обнаружить утечки памяти и риски OOM.

**Ярлыки:** не требуются

### Kb transferred (received) / provided (sent) for shop API
**Зачем нужна:**

**Ярлыки:**
- `endpoint`

# Дополнительное задание

Для ключевых компонентов системы определены показатели насыщенности, превышение которых приводит к деградации сервиса и росту числа ошибок.

## MES API

**Показатели насыщенности:**
- CPU utilization > 80% в течение 5 минут
- Memory utilization > 85%
- Number of simultaneous sessions > рассчитанного лимита

**Обоснование:**  
MES API — центральная точка обработки заказов.  
При превышении данных порогов резко растёт latency и количество ошибок 5xx.

**Реакция системы:**
- Срабатывает алерт высокой критичности
- Автоматическое добавление инстансов сервиса
- Создание инцидентного тикета для команды эксплуатации

## Shop API

**Показатели насыщенности:**
- CPU utilization > 75%
- Response time p95 > 1.5 секунды
- Number of simultaneous sessions > допустимого значения

**Обоснование:**  
Задержки напрямую влияют на конверсию и количество оформленных заказов.

**Реакция системы:**
- Уведомление дежурной команды
- Горизонтальное масштабирование сервиса
- Мониторинг динамики конверсии

## CRM API

**Показатели насыщенности:**
- CPU utilization > 80%
- Response time p95 > 2 секунды
- Number of requests (RPS) выше ожидаемого пика

**Обоснование:**  
Перегрузка CRM замедляет работу операторов и увеличивает backlog заказов.

**Реакция системы:**
- Уведомление команды поддержки
- Приоритизация внутренних запросов
- Создание тикета на оптимизацию

## PostgreSQL

**Показатели насыщенности:**
- Number of connections > 85% от лимита
- Memory utilization > 80%
- Рост latency запросов

**Обоснование:**  
Насыщение БД приводит к цепной деградации всех API.

**Реакция системы:**
- Алерт высокой критичности
- Ограничение новых соединений
- Уведомление DBA

## RabbitMQ

**Показатели насыщенности:**
- Number of messages in flight растёт непрерывно
- Dead-letter-exchange messages > допустимого порога

**Обоснование:**  
Указывает на остановку или деградацию обработки заказов.

**Реакция системы:**
- Алерт
- Приостановка приёма новых сообщений
- Создание инцидента для команды интеграций
