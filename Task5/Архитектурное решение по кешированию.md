# Что имеет смысл кешировать

**1. Shop API (публичная часть)**
- Каталог товаров, опции, цены, справочники
- Причина: высокая частота чтения, редкие изменения  
- Кеш: Redis / in-memory, TTL + инвалидция по событиям

**2. Метаданные 3D-файлов**
- Объём, вес, предварительные расчёты, превью
- Причина: тяжёлые вычисления и повторные запросы
- Кеш: Redis (ключ = hash файла)

**3. Статусы заказов (read-only view)**
- Для Internet Shop и CRM
- Причина: частые polling/refresh, данные меняются через события
- Кеш + обновление через RabbitMQ events

**4. MES API – расчёт цены**
- Результаты расчёта по одинаковым входным параметрам

# Мотивация

Внедрение кеширования предлагается для снижения нагрузки на backend-сервисы и базы данных, а также для улучшения времени отклика системы в пользовательских сценариях с высокой долей чтения.

**Проблемы, которые решает кеширование:**
- Высокая нагрузка на Shop API и CRM API из-за частых read-запросов
- Повторные тяжёлые вычисления (расчёт параметров и цены 3D-моделей)
- Частые запросы статусов заказов из UI (polling)
- Рост латентности при масштабировании числа клиентов

**Ожидаемый эффект:**
- Снижение RPS к PostgreSQL
- Уменьшение времени ответа API
- Повышение стабильности системы при пиковых нагрузках
- Улучшение UX для Customer и Seller

# Предлагаемое решение

## Тип кеширования
Выбираем серверное кеширование, а не клиентское.

**Почему серверное:**
- Единая точка контроля TTL/инвалидации и политики консистентности
- Снижение нагрузки на БД и backend для всех клиентов сразу
- Безопаснее (клиентский кеш сложнее контролировать, выше риск устаревших данных и утечек)
- Упрощает масштабирование UI (клиенты становятся "тоньше")

## Паттерны кеширования 

**Cache-Aside (основной паттерн)**

Применяем для:
- каталогов/справочников Shop API
- статусов заказов (read-only view)
- метаданных 3D-файлов
- результатов расчёта цены (если входные параметры идентичны)

**Почему Cache-Aside:**
- Просто внедряется без изменения write-потока
- Хорошо подходит для read-heavy данных и вычислимых результатов
- Позволяет контролировать TTL и инвалидировать по событиям (RabbitMQ)

**Почему хуже Write-Through:**
- Усложняет запись (каждый write обязан синхронно обновлять кеш)
- Не даёт выгоды для вычислимых данных (например, расчёт цены/метаданных), где запись в БД может отсутствовать
- Повышает латентность записи и связность компонентов

**Почему хуже Refresh-Ahead (как основной):**
- Требует предсказания "горячих" ключей и фоновых джоб
- Риск лишней нагрузки (прогрев того, что не будет запрошено)
- Сложнее эксплуатация; оправдано только для небольшого набора реально горячих сущностей

## Стратегия инвалидации кеша

Выбираем гибридную стратегию:
1) **Event-driven (программная) инвалидация по ключу** для изменяемых сущностей (статусы/заказы) через события из RabbitMQ  
2) **Временная инвалидация (TTL)** как дополнительная

**Обоснование:**
- Статусы заказов меняются по событиям. Логично инвалидировать сразу после `OrderStatusChanged`
- Для `orders:list:*` ключей слишком много вариантов (фильтры, пагинация). TTL проще и стабильнее, чем пытаться идеально вычислить все затронутые ключи
- TTL защищает от рассинхронизации

**Что инвалидируем:**
- `order:status:<orderId>` — удаляем/обновляем точечно по событию
- `orders:list:<...>` — либо:
  - точечно по "тегам" (если реализуем индекс/тегирование ключей по userId/shopId), либо
  - не трогаем массово, полагаемся на короткий TTL

## Сравнение стратегий

| Стратегия A: Event-driven delete/update (по ключу) | Стратегия B: TTL-only (только временная) | Остальные (wildcard purge, write-through invalidation) |
| --- | --- | --- |
| **Лучше подходит для статусов и точечных сущностей**, потому что: 1) минимальная устарелость данных (почти real-time) 2) маленькая зона воздействия (только нужные ключи) 3) хорошо ложится на текущую MQ архитектуру | **Лучше подходит для списков** (filters/page), потому что: 1) не требует сложного учета всех ключей 2) проще эксплуатация 3) предсказуемая нагрузка на Redis | **Wildcard purge (`DEL orders:list:*`)**: плохо масштабируется. **Write-through / sync invalidation на записи**: усложняет кейс с записью, увеличивает латентность и связность сервисов и дороже в сопровождении |
 
**Почему не выбирать только одну стратегию:**
- Только event-driven: сложно корректно инвалидировать все варианты `orders:list` ключей (фильтры/пагинация), риск ошибок и постоянного усложнения
- Только TTL: возможна заметная устарелость статуса сразу после изменения (особенно в UI критично)
