# Существующие проблемы:
  - Проблемы работы с клиентами
    - Жалоб от клиентов на просроченные заказы стало больше.
    - Через месяц после открытия API компания потеряла уже несколько крупных контрактов из-за проблем с заказами. 
    - Недовольство клиентов онлайн-магазина (B2C) растёт.
  - Проблемы внешних пользователей
    - Жалобы со стороны пользователей. 
      Клиенты и представители компаний ежедневно сообщают, что не получили свои заказы. (как через фронт, так и через API)
  - Проблемы от операторов
    - Когда они заходят на первую страницу MES, система долго прогружается. 
      На первой странице отображается список заказов в работе по статусам — это дашборд с фильтром.
  - Проблемы окружения:
    - Каждое приложение имеет по одному инстансу (нет горизонтадльного масштабирования)
    - Базы данных имеют один инстанс, который работает на запись и на чтение.
  - Проблемы DevOps :
    - В release-окружения версию деплоят вручную.
    - В продакшн версию деплоят вручную.
  - Проблемы эксплуатации:
    - Нет мониторинга
    - Нет логирования
    - Нет траммировки

# Потенциальные проблемные места:
  - MES API 
    - Высоконагруженное приложение с множеством пользователей (Операторы / Внешние системы / Очереди)
  - CRM
    - Нет собственного хранилища данных - сложность синхранизации изменений в системах так как ужно договариваться о структуре БД.

  - Observability
    - Нет мониторинга
    - Нет логирования
    - Нет траммировки

# Инициативы:
  - MES API
    - Разделение пользователей
    - RateLimit для внешних пользователей
    - Вынести в другой сервис

  - PostgreSQL

  - Observability
    - Внедрить мониторинг
    - Отслеживать бизнес-метрики об удволетворении пользователей

    - Внедрить логирование

# Приоритеты

## Подход к приоритизации

Приоритизация инициатив выполнялась на основе следующих критериев:

1. **Влияние на клиентов и выручку**  
   Рост числа жалоб, потеря контрактов и недовольство B2C-клиентов напрямую влияют на бизнес.
2. **Снижение операционных рисков**  
   Отсутствие наблюдаемости и ручные процессы делают систему нестабильной и трудноуправляемой.
3. **Масштабируемость и устойчивость архитектуры**  
   MES API и базы данных являются узкими местами при росте нагрузки.
4. **Time-to-value**  
   Приоритет отдан инициативам, которые можно реализовать за 6 месяцев и быстро получить эффект.

## Приоритеты инициатив

### Критический приоритет

1. **Observability**
   - Внедрение мониторинга
   - Централизованное логирование
   - Трассировка (в первую очередь для MES API)

2. **Стабилизация MES API под нагрузкой**
   - RateLimit для внешних пользователей
   - Разделение пользователей (операторы / внешние клиенты / очереди)
   - Горизонтальное масштабирование MES API

### Высокий приоритет

3. **Архитектурное разукрупнение MES API**
   - Вынос расчёта стоимости заказа в отдельный сервис
   - Вынос логики назначения заказов операторам в отдельный сервис

4. **Разделение баз данных Магазина и CRM**
   - Снижение связанности между системами
   - Упрощение изменений схем данных
   - Подготовка к независимому масштабированию

### Средний приоритет

5. **Автоматизация CI/CD**
   - Автоматический деплой в release-окружения
   - Контролируемый деплой в production (blue/green или canary)

6. **Внедрение бизнес-метрик удовлетворённости клиентов**
   - SLA по обработке заказов
   - Процент просроченных заказов
   - Time-to-delivery


# Целевая архитектура через 6 месяцев

## Архитектура приложений
- MES API — stateless-сервис с горизонтальным масштабированием
- Выделенные сервисы:
  - Pricing Service
  - Order Assignment Service
- Чётко определённые зоны ответственности между MES, CRM и Online-магазином

## Хранение данных
- Отдельные PostgreSQL-инстансы:
  - Магазин
  - CRM
- Возможность использования read-replica для аналитики и дашбордов

## Эксплуатация и наблюдаемость
- Единый стек observability:
  - Метрики (latency, error rate, throughput)
  - Централизованные логи
  - Трассировка
- Прозрачность цепочки обработки заказа от клиента до доставки

## Процессы разработки и эксплуатации
- Минимизация ручных операций
- Предсказуемые и воспроизводимые деплои
- Снижение MTTR при инцидентах

# Топ-3 инициативы при ограничении ресурсов

Если в течение ближайших 6 месяцев возможно реализовать только три инициативы, приоритет будет следующим:

## 1. Observability (мониторинг, логирование, трассировка)

**Обоснование:**  
В текущем состоянии система является «чёрным ящиком». Без наблюдаемости невозможно:
- определить причины потери заказов,
- доказательно разбирать инциденты,
- принимать обоснованные архитектурные решения.

Observability является фундаментом для всех последующих изменений.

## 2. RateLimit и разделение пользователей в MES API

**Обоснование:**  
Позволяет защитить критические бизнес-процессы от перегрузки внешними пользователями и интеграциями.  
Даёт быстрый эффект в снижении количества ошибок и жалоб клиентов.

## 3. Горизонтальное масштабирование MES API

**Обоснование:**  
MES API является центральной точкой отказа.  
Горизонтальное масштабирование:
- снижает latency,
- повышает отказоустойчивость,
- подготавливает систему к росту нагрузки.
