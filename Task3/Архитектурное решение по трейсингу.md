# Анализ

## Компоненты, которые необходимо покрыть трейсингом

### Internet Shop (Frontend)
- Точка входа заказов B2C
- Возможны проблемы при создании заказа, загрузке 3D-файлов, отправке данных в API

### Shop API
- Обрабатывает заказы клиентов
- Сохраняет данные в Shop DB
- Загружает файлы в 3D storage

### 3D Files Storage (S3)
- Асинхронная и внешняя зависимость
- Критична для расчёта стоимости заказа

### CRM API
- Участвует в обработке заказов и изменении их статусов
- Отправляет события в очередь

## Message Queue (RabbitMQ)
- Асинхронная передача событий о заказах
- Ключевой элемент интеграции между сервисами

## MES API
- Центральный сервис обработки заказов
- Рассчитывает цену
- Назначает заказы операторам

### MES UI (Frontend операторов)
- Конечная точка обработки заказа человеком

## Ключевые места, где заказ может сломаться или зависнуть

1. Создание заказа в Shop API
2. Загрузка 3D-файлов в S3
3. Отправка события о заказе в RabbitMQ
4. Получение и обработка события MES API
5. Расчёт цены заказа
6. Назначение заказа оператору

Эти этапы должны быть объединены в единый trace

## Данные, которые должны попадать в трейсинг

###  Контекст запроса
- источник заказа (`channel`: web / api / crm)
- тип пользователя (`user_type`: customer / api_user / operator)
- endpoint / operation name
- HTTP method

### Тайминги
- время начала и окончания каждого span
- latency операций:
  - API-запросов
  - загрузки файлов
  - обработки сообщений
  - расчёта цены

### Результаты выполнения
- статус операции (success / error)
- HTTP status code
- тип ошибки
- retry count (если есть)

### Асинхронные взаимодействия
- message_id
- queue / topic name
- время публикации и обработки сообщения
- признак попадания в dead-letter

# Мотивация внедрения трейсинга
Внедрение distributed tracing позволяет получить сквозную прозрачность жизненного цикла заказа — от момента его создания клиентом до передачи в производство и обработки оператором.

## Что даст трейсинг компании

1. **Сокращение времени расследования инцидентов**  
    Позволяет быстро определить конкретный сервис и этап, на котором произошёл сбой или задержка, что напрямую снижает MTTR.

2. **Повышение надёжности обработки заказов**  
    Даёт возможность выявлять узкие места в цепочке обработки заказов и устранять их до того, как они начнут влиять на клиентов.

3. **Прозрачность работы API-интеграций**  
    Позволяет видеть реальную картину поведения внешних клиентов и интеграций, а также их влияние на общую стабильность системы.

4. **Связь технических проблем с бизнес-результатами**  
   Трейсинг позволяет напрямую связать технические задержки и ошибки с потерей заказов, просрочками и недовольством клиентов.

5. **Основа для масштабирования и оптимизации архитектуры**  
    Данные трейсинга дают объективную основу для принятия решений о рефакторинге, выносе сервисов и масштабировании компонентов.

## Метрики, на которые влияет внедрение трейсинга

### Технические метрики

1. **MTTR (Mean Time To Recovery)**  
   Снижается за счёт точного определения проблемного сервиса и операции в распределённой цепочке.

2. **End-to-end latency обработки заказа**  
   Позволяет измерять реальное время прохождения заказа через все сервисы и выявлять самые медленные этапы.

3. **Процент ошибок в распределённых сценариях**  
   Упрощает анализ причин ошибок, возникающих на стыке сервисов или в асинхронных взаимодействиях.

### Бизнес-метрики

4. **Процент успешно обработанных заказов**  
   Повышается за счёт сокращения «потерянных» и зависших заказов.

5. **Доля просроченных заказов**  
   Снижается благодаря своевременному выявлению задержек в цепочке обработки.

# Компромиссы

## Асинхронные и внешние компоненты

**Описание:**  
Часть взаимодействий в системе проходит через асинхронные каналы (RabbitMQ) и внешние сервисы (S3-совместимое хранилище).

**Компромисс:**  
- Трейсинг не всегда может автоматически связать асинхронные операции в единый trace.
- Требуется ручная передача контекста (`trace_id`) в сообщения очереди и метаданные запросов.

**Почему это дорого:**  
- Необходимы доработки продюсеров и консюмеров сообщений.
- Повышается сложность кода и поддержки.

## Frontend-часть

**Описание:**  
Internet Shop и MES UI работают в браузере и зависят от пользовательского окружения.

**Компромисс:**  
- Трейсинг не покрывает сетевые задержки, вызванные клиентским устройством, браузером или интернет-каналом пользователя.
- Возможна лишь частичная корреляция frontend-спанов с backend-трейсами.

**Почему это ограничение:**  
- Клиентская часть не находится под полным контролем компании.
- Сбор детального трейсинга может негативно влиять на производительность клиента.

## Низкоуровневые операции баз данных

**Описание:**  
PostgreSQL используется несколькими сервисами и выполняет большое количество запросов.

**Компромисс:**  
- Детальный трейсинг каждого SQL-запроса может привести к значительным накладным расходам.
- Чаще используется агрегированная информация (slow queries, timing), а не полноценные spans.

**Почему это разумно:**  
- Полный трейсинг БД не всегда даёт дополнительную ценность по сравнению с метриками и логами.
- Стоимость хранения и обработки таких данных высока.

## Высокая нагрузка и стоимость хранения данных

**Описание:**  
MES API и Shop API являются высоконагруженными сервисами.

**Компромисс:**  
- Полный трейсинг 100% запросов приведёт к значительным затратам на хранение и обработку данных.
- Требуется использование sampling (выборочного трейсинга).

**Почему это необходимо:**  
- Без sampling система трейсинга может сама стать узким местом.
- Бизнес-ценность большинства трасс одинакова, достаточно репрезентативной выборки.

## Наследственные и сторонние компоненты

**Описание:**  
Часть компонентов может быть устаревшей или сторонней (проприетарной).

**Компромисс:**  
- Невозможно или слишком дорого внедрить трейсинг без серьёзных доработок.
- Приходится ограничиваться логами и метриками.

**Почему это допустимо:**  
- Трейсинг наиболее ценен на границах сервисов и бизнес-процессов.
- Полное покрытие системы не всегда оправдано экономически.

# Безопасность системы трейсинга

## Аутентификация и доступ
- Доступ к системе трейсинга только для аутентифицированных сотрудников
- Использование корпоративного SSO
- Ролевой доступ:
  - Support — просмотр трасс
  - Dev — детальный анализ
  - Admin — управление системой
- Анонимный доступ запрещён

## Ограничение внешнего доступа
- Доступ к интерфейсу трейсинга только из внутренней сети
- Внешний доступ — через VPN или bastion-host
- Прямой доступ из интернета запрещён

## Защита данных
- Передача данных трейсинга только по TLS
- Аутентификация сервисов при отправке трасс
- Запрет передачи персональных и платёжных данных
- Использование только технических идентификаторов (order_id, client_id)

## Контроль и аудит
- Разграничение доступа по окружениям (prod / stage)
- Логирование действий пользователей в системе трейсинга
- Ограничение доступа к production-трейсам
