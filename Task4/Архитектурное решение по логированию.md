# Анализ

## Какие системы логируем
- Shop API
- CRM API
- MES API
- RabbitMQ
- Shop DB (PostgreSQL)
- MES DB (PostgreSQL)
- 3D files storage (S3)
- Frontend (Internet Shop, CRM, MES) — только ключевые события и ошибки

## Обязательные поля логов
- `timestamp`, `level`, `service`
- `request_id` / `correlation_id`
- `order_id`
- `user_type` (customer / api_user / operator)
- `client_id` / `operator_id` (если применимо)
- `event`, `status`

## INFO-логи

**Shop API**
- Создание заказа (order_id, customer_id, time)
- Загрузка 3D-файла (order_id, file_id, status)
- Изменение статуса заказа

**CRM API**
- Получение заказа
- Изменение статуса заказа
- Отправка события в очередь

**MES API**
- Получение заказа
- Расчёт цены (start / finish)
- Назначение заказа оператору
- Изменение статуса заказа

**RabbitMQ**
- Публикация сообщения
- Получение сообщения
- Попадание сообщения в DLQ

**Базы данных**
- Ошибки подключения
- Медленные запросы (с порогом)

**S3**
- Загрузка файла
- Ошибка доступа

**Frontend**
- Отправка заказа
- Ошибка, показанная пользователю

# Мотивация

## Что даёт логирование

- Быстрое расследование ошибок и инцидентов
- Снижение времени восстановления сервиса (MTTR)
- Понимание причин потери заказов
- Основа для масштабирования и внедрения трейсинга

## Метрики, на которые влияет логирование

**Технические:**
- MTTR  
- Количество необъяснённых ошибок  
- Частота инцидентов  

**Бизнес:**
- Процент успешно обработанных заказов  
- Количество обращений в поддержку  

## Приоритет внедрения

Так как команда ограничена в ресурсах, логирование и трейсинг внедряются поэтапно.

**Первая очередь:**
1. **MES API** — центральная точка обработки заказов  
2. **Shop API** — точка входа заказов клиентов  
3. **RabbitMQ** — асинхронные интеграции и риск потери сообщений  

**Вторая очередь:**
- CRM API  
- Базы данных  
- Frontend и S3

# Предлагаемое решение

## Как реализуем
- Формат логов: структурированный JSON
- Сбор:*агент на хостах/в кластере (например, Fluent Bit / Vector)
- Хранилище и поиск: централизованная система логов OpenSearch
- Визуализация: дашборды Kibana
- Корреляция: в каждый лог добавляем `request_id` и (если есть) `trace_id`, `order_id`

## Что внедрить/доработать
- В **Shop API / CRM API / MES API**:
  - добавить JSON-логгер и единые поля (`order_id`, `user_type`, `client_id`, `request_id`)
  - логировать ключевые события: создание/изменение статуса заказа, публикация/получение сообщения, расчёт цены
- В **RabbitMQ**:
  - включить сбор системных логов + фиксировать DLQ события
- В **PostgreSQL**:
  - включить логи ошибок + slow queries (с порогом)
- В **S3**:
  - включить access/error логи
- Добавить алерты по логам (рост 5xx, критические ошибки заказа)

## Политика безопасности логов

- Доступ только через **SSO** и **RBAC**:
  - Support — чтение
  - Dev — чтение + расширенный доступ
  - Admin — управление
- Доступ к логам только из внутренней сети (VPN/bastion)
- **Запрет PII**: не логировать имена/телефоны/адреса/платёжные данные и содержимое файлов
- Маскирование/редакция полей на стороне приложения или коллектора (redaction)
- Аудит доступа к логам (кто смотрел/что искал)

## Политика хранения логов

- Разделение по окружениям: **отдельные индексы/тенанты** `prod` и `stage`
- Хранение:
  - `prod`: **30 дней** (расследование инцидентов/претензий)
  - `stage`: **7 дней**
- Ограничение объёма:
  - sampling/ограничение DEBUG в prod
  - ротация и сжатие
- Управление жизненным циклом (ILM/retention policies): автоматическое удаление по сроку

# Анализ логов

## Алертинг

Алерты на основе логов:
- рост количества ERROR
- появление критичных событий (заказ не создан, DLQ)
- резкий рост WARN
- отсутствие ожидаемых событий (нет заказов)

Реакция:
- уведомление дежурной команды
- создание тикета при критических инцидентах

## Поиск аномалий
Да, в базовом виде.

Примеры:
- резкий рост событий `order_created` (возможный DDoS)
- всплеск логов от одного `client_id` или IP
- нетипичный рост ошибок по endpoint
- рост DLQ без увеличения нагрузки
